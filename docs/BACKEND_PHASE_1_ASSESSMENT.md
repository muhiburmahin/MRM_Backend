# Phase 1 — Bangladesh Website Benchmark and Backend Assessment

**Assessment date:** 12 October 2026  
**Repository inspected:** `MRMinfotech-backend`  
**Scope:** Public-site benchmark and read-only review of current source, Prisma schema/configuration, tests, and project documentation. This report does not implement features, change API behavior, modify schemas, or perform database operations.

## 1. Executive summary

The repository supports an **admin-managed corporate website for MRM Infotech**, not a public e-commerce marketplace, booking platform, or multi-tenant SaaS. The project documentation describes services, product offerings, projects/case studies, team, blog, FAQs, testimonials, company information, contact leads, media, SEO, and an admin-controlled website. It also states the project is not SaaS and that the public website and admin UI are separate applications. These are the strongest available scope signals; the referenced source SRS was not found in the inspected documentation, so some requirement details remain unconfirmed.

The current source is materially more complete than several older documents claim. `AppModule` registers authentication, core admin, and 11 resource modules. There are public content routes, protected admin routes, server-side cookie sessions, RBAC permission checks, input validation, and working mocked tests. Nevertheless, build/test success is not production readiness:

- No Prisma migration files exist; extra SQL constraints are written but unapplied. No live PostgreSQL startup, migration, seed, or API smoke test was performed.
- Admin APIs are missing for some explicitly documented website-management needs (notably dynamic pages and navigation; theme management is also absent). Other schema-backed domains such as careers and subscribers are not confirmed as product requirements.
- Media APIs register metadata only; no binary upload or configured storage integration was verified.
- 4 nested resource test suites fail to compile due missing helper imports; 2 nested specs pass 5 tests but are service-level tests rather than HTTP E2E coverage. The configured root E2E suite passes 35 tests.
- Authentication/RBAC exists, but 2FA, a supported first-owner operator command, email delivery, and consistent audit/revision coverage do not.
- Formatting fails for 51 TypeScript files; lint, typecheck, build, Prisma validation, unit tests, and configured E2E tests pass.
- Production deployment, monitoring/alerting, shared rate limiting, backup/restore, and disaster recovery have not been verified.

No competitor’s visible feature is treated as a requirement for this project. No private competitor backend architecture is inferred. No production-readiness or “100% complete” claim is warranted.

## 2. Methodology and evidence boundaries

### Repository review

Current source was treated as primary evidence. Review covered module registration, controllers/routes, active auth and authorization guards, selected services and DTO behavior, Prisma models and SQL constraints, validation/error configuration, test configuration and outcomes, package scripts, and project documentation. The `.env` file and secret values were not read or printed.

The workspace has no Git metadata, so a Git diff could not be used to identify pre-existing local changes. No database mutation or production request was made.

### Bangladesh website inspection

Official public company sites were inspected on 12 October 2026 using homepage/link-level inspection. A feature is called **observed** only when visible in the inspected material. A listed route/page link does not prove that the destination workflow works. Mobile responsiveness, account creation, checkout, payment, booking, and private backend behavior were not tested unless explicitly stated.

“Not verified” means it was not established in the inspected pages; it does **not** mean the company lacks the feature or policy. Backend capabilities in the table are inferences from visible site functions, not claims about private systems.

## 5. Current backend architecture and module inventory

### Architecture

- NestJS 11 modular monolith; PostgreSQL via Prisma 6.19.3.
- URI-versioned API under `/api/v1`; validation, exception formatting, Helmet, exact-origin credentialed CORS, throttling, request IDs, and Pino logging are configured.
- `AppModule` wires database, auth, admin, health, and 11 resource modules: Blog, Company, Contact, FAQs, Media, Products, Projects, Services, Site Settings, Team, and Testimonials.
- Prisma schema has 63 models, 14 enums, 100 relation annotations, 13 compound unique declarations, and 37 indexes.
- There are zero migration files under `prisma/migrations`. `prisma/sql/constraints.sql` describes trust, contactability, pricing-parent, and unique-active/default constraints, but is not applied.
- Application startup connects Prisma to PostgreSQL. Mocked tests do not establish actual DB compatibility or startup success.

### Functionality and verification labels

- **Implemented:** route/service/model code exists and is registered or used.
- **Tested:** a relevant test assertion actually ran and passed; test scope is identified (unit or mocked HTTP).
- **Isolated-running verified:** a running Nest test application exercised a route with fake/mock database dependencies. This is stronger than a unit test but not a live DB/deployment test.
- **Production-ready:** deployed configuration, migration, security, monitoring, backup/recovery, and operational acceptance have been demonstrated. This status has **not** been reached or established.

### Contract, validation, and discovery notes

- Global `ValidationPipe` transforms DTOs, whitelists fields, rejects unknown properties and unknown values.
- Resource DTOs use validation and services map several Prisma constraint errors into HTTP errors. Controller response documentation is not consistently explicit; some Swagger response decorators do not declare a response DTO.
- Public Blog, Products, FAQs, Services, Projects, Team and Testimonials contain locale resolution/fallback logic to varying degrees. Seeded locales are `en` and `bn`; translation completeness and frontend language switching were not end-to-end tested.
- SEO title/description fields are represented for some translated content. No canonical URL, sitemap, robots, or structured-data route was found.
- Search is resource-specific where implemented; there is no verified cross-site search endpoint.
- API pagination response shape is not fully consistent: the API guide describes `{ items, meta }`, while Contact and Media services return `{ data, meta }` (and Blog also uses `data`). Confirm frontend contracts before normalizing anything.
- No duplicate active feature route was established. The separate unused legacy permissions guard is redundant/confusing and should not be mistaken for the registered session permission guard.

Phases 3–5 are proposed, not authorized implementation work in this Phase 1.
