## 4. Required workflow proposals and measurable acceptance criteria

The workflows below are proposed based on documented corporate-site purpose. Acceptance criteria remain pending owner approval; they are not promises that current APIs already satisfy them.

### 4.1 Public corporate content

**Purpose and journey:** visitors discover the company, services/software offerings, case studies, team, FAQs, testimonials and articles; they navigate between public pages and then submit an inquiry.

**Actors:** anonymous visitor; authenticated content editor; publisher/approver role if the owner requires separation.

**Public behavior:** GET-only content routes return currently published and eligible translations; no draft/private content or internal audit data. Locale selection follows the existing resource behavior until a single policy is signed.

**Admin behavior:** editors create/update localized records. Publication is only available to actors with the relevant publish permission where currently implemented. Delete is blocked when references/invariants require it, or returns a documented conflict.

**Data/validation:** validate identifiers, slugs, locale codes against enabled Languages, required fields per translation, URLs, media references, list limits, sort fields and publication dates. Unknown fields remain rejected. No arbitrary HTML/JS or unconstrained page blocks without a signed sanitizer/schema policy.

**URL/localization:** existing resource URLs remain stable. Translation slug collisions return conflict. Locale fallback must not expose a draft; owner must select default and missing-translation behavior per resource.

**Privacy/audit:** public response selection excludes internal notes, staff email, hashes and evidence that is not intended for public output. Required audit/revision event matrix is unresolved.

**Acceptance criteria (proposed):**

1. Anonymous GETs return only approved published records, at or before publication time; draft, future, unverified, unconsented or non-public records are not returned where the domain requires those rules.
2. Unsupported/disabled locale behavior and fallback are consistent with approved policy and covered for `en` and `bn`.
3. Admin reads/mutations require valid session and exact permission; missing session returns 401, insufficient permission 403, invalid DTO/unknown property 400, missing entity 404, duplicate/in-use conflict 409.
4. Every create/update validates media/taxonomy relationships and returns a stable response contract; no raw Prisma row with internal fields is leaked.
5. Slug/translation uniqueness is enforced in application and database; approved DB invariants are tested on real PostgreSQL.
6. Approved create/update/publish/unpublish/delete events appear in audit history according to the signed audit policy.

### 4.2 Contact submission and lead operations

**Purpose and journey:** visitor submits a contact/demo/project inquiry with approved consent; authorized staff review, assign, update status, add internal note, and soft-delete per approved retention rules.

**Public behavior:** current `POST /api/v1/contact` accepts `CreateContactDto`; service requires `consentGiven === true`, writes a `Lead` with generated ref/type `GENERAL`, stores optional subject in payload, and returns a generic thank-you message. Current API has no verified CAPTCHA/honeypot/shared limiter/email delivery.

**Admin behavior:** list/filter/search with `lead:read`, detail including internal notes with `lead:read`, update status/assignee/note with `lead:write`, soft delete with `lead:delete`. Assignment is global, not row-owner scoped.

**Privacy/security:** only collect approved contact fields; do not return notes on public APIs. Consent wording/version, permitted staff access, notification recipients, retention and hard-deletion/legal hold policy remain owner decisions. Avoid including inquiry PII in logs/notification URLs.

**Acceptance criteria (proposed):**

1. Valid public requests are validated and create exactly one lead with server-generated reference and server-generated consent timestamp; client cannot choose internal status, assignee or ID.
2. Missing/false consent, malformed contact data, oversized message, unknown field and invalid source values return 400 without a record.
3. Lead list honors approved filters/sort/page bounds and excludes soft-deleted leads. Unauthorized access tests assert 401/403 for every permission boundary.
4. Status transitions, assignment, and internal notes are atomic with corresponding status history; nonexistent assignee is rejected without partial write.
5. Public failure uses a stable generic response; internal error is logged safely without raw PII/secrets. Notification behavior (if approved) has retry/idempotency/failure test cases.
6. Spam limits apply at the approved enforcement layer and are tested under the deployment’s intended replica model.
7. Approved retention job/operation deletes or anonymizes data according to policy and is tested on a disposable DB; no deletion policy is assumed here.

### 4.3 Media metadata and optional binary handling

**Current journey:** privileged staff can register provider-neutral media metadata, list/get it, and delete metadata if references are absent. Current endpoint explicitly does not upload or delete stored bytes.

**Security requirements:** actor identity is server-derived; metadata validates provider-relative `storageKey`, URL, MIME/size fields and localized image alt text. A media reference inventory must match all content fields. Decide whether media is public/private before any signed URL or direct upload contract is designed.

**Acceptance criteria (proposed):**

1. Metadata CRUD requires specified media permissions; client-supplied uploader identity is rejected/ignored as appropriate by the current DTO contract.
2. Duplicate storage key and in-use references return documented 409; missing ID 404; malformed URL/key/locale/size 400.
3. Reference deletion is atomic or database-enforced; tests prove a concurrent content reference cannot become dangling.
4. For the owner-approved backend-proxied upload direction, actual bytes (not only declared extension/MIME) are validated; approved size limits are enforced; scanning/re-encoding and safe object naming are specified; failed upload does not leave orphan metadata/bytes; public/private delivery and deletion are tested.
5. If upload is not approved, external storage actor/provider and metadata contract are documented; backend does not claim to upload files.

### 4.4 Admin identity, permissions and audit

**Current journey:** admins sign in by email/password; session cookie identifies actor; role permissions are checked per request; admin can manage users, roles, invites, sessions and audit logs. Invite acceptance sets a password. The first-owner provisioning service is internal and no CLI/API command is verified. 2FA-enabled accounts are refused.

**Acceptance criteria (proposed):**

1. Invalid/inactive/locked accounts return generic failure; no password/session/invite hashes in any response or log; session revocation makes old cookie invalid.
2. All non-public routes fail closed; test unauthenticated and insufficient permission for every protected route family.
3. Owner self-escalation and last-owner protections are concurrency-tested and cannot leave zero active owners if that invariant is required.
4. Only the approved bootstrap method can create the first owner; it is one-time, requires policy-compliant secure input, records audit event, and cannot be raced/replayed.
5. MFA/recovery behavior is internally consistent: enrollment is not allowed unless the complete verification/recovery/login flow is supported.
6. Audit actions and failure semantics follow the approved event matrix; unauthorized actors cannot read audit logs.

### 4.5 Pages, navigation, theme and SEO — target behavior awaiting sign-off

These are documented-scope candidates but have no current APIs. Before API implementation, owner must sign page types, block allowlist/schema, URL and translation rules, menus, theme fields, SEO outputs, permissions, caching and audit semantics.

**Proposed acceptance criteria once requirements are approved:** staff-only draft CRUD; public only published content; bilingual behavior and slug collision cases tested; path validation and redirect policy explicit; page blocks schema-validated and safe to render; navigation ordering/links validated; theme activation is atomic; public SEO response has tested metadata and canonical/sitemap behavior only if backend is responsible. No endpoint path or payload is approved by this document.

## 5. Existing API contract inventory (read-only; no contract changes approved)

### Global contract

- Prefix/version: `/api/v1`; Swagger at `/docs` depends on environment config.
- DTOs are validated through a global transforming `ValidationPipe` with whitelist, unknown-field rejection and unknown-value rejection.
- Error body is `{ statusCode, error, message, requestId?, path, timestamp }`; `message` may be a string or string array. Expected common statuses: 400 validation, 401 no valid session, 403 denied/origin failure, 404 missing entity, 409 conflict, 429 throttle, 500 unexpected error, 503 readiness failure.
- Authentication uses server-side session cookies, not bearer tokens. State-changing cookie requests require allow-listed `Origin` (or `Referer`); CORS allows only the intersection of configured exact `CORS_ORIGINS` and `AUTH_ALLOWED_ORIGINS`.
- Collection contracts are inconsistent: guide describes `{ items, meta }`; Contact, Media and Blog return `{ data, meta }`; service-specific implementations need contract tests. Do not normalize without frontend approval.
- Standard HTTP response structures are service DTO/mappers, but Swagger response documentation is incomplete/inconsistent. Some create/update routes return mapped entity objects, content delete routes vary (200 vs 204), and exact per-resource response fields should be taken from current service mapper/DTO files rather than assumed uniform.
- `GET /api/v1/auth/me` and `GET /api/v1/admin/me` expose overlapping current-user profile use cases. This may be intentional compatibility or unnecessary duplication; retain both until the frontend consumer is identified and an owner approves consolidation.
- `src/common/guards/permissions.guard.ts` is a legacy fail-closed guard with a different decorator metadata contract; the active session-aware guard is in `src/auth/guards/permissions.guard.ts`. It is not evidence of a second live permission API, but it creates maintenance/test confusion.

### D. Admin Dashboard and authorization details

- Current `GET /api/v1/admin/dashboard` returns aggregate counts; it does not establish a recent-activity feed.
- Active auth is server-side session cookie, password hashing, login lockout, per-request permissions, global fail-closed guards, exact-origin credentialed CORS and `OriginGuard` for state-changing cookie requests. These controls are source-verified and selected paths have unit/mocked E2E tests; production cookie/domain/proxy behavior is not verified.
- Current admin APIs use resource permissions where implemented. Seed defines `page:*`, `nav:write`, `theme:*`, lead, media and admin permissions, but permission rows are not equivalent to registered routes or enforced functionality.
- Existing active routes generally use global admin permissions, not record-owner/tenant policies. Product scope has no multi-tenant behavior. Contact Lead assignment currently has a User FK but not assignment-based access restrictions.
- `AuthProvisioningService` can create a first owner only when no owner exists, with a required password change and an audit record. It is not a CLI or HTTP workflow; count-then-create is not a demonstrated concurrency guarantee.
- 2FA is not supported; login denies 2FA-enabled users. Password reset/recovery and invitation email delivery are absent.
- `GET /api/v1/auth/me` and `GET /api/v1/admin/me` overlap; do not consolidate until the separate frontend consumer is reviewed.
- `src/common/guards/permissions.guard.ts` is a legacy fail-closed implementation using different metadata and is not the registered active auth permissions guard. Avoid using its tests as proof of active RBAC.

### E. Media upload conflict, evidence, and recommended minimum design

#### What is actually implemented

1. There is **no binary multipart upload endpoint**. The registered media controller accepts a JSON `UploadMediaDto`.
2. No uploaded bytes are persisted by the backend; no local disk/object storage integration was found. `MediaAsset.storageKey` is described by schema as an object-storage key, and the DTO/service record an external storage key and URL.
3. The caller supplies `storageKey`, `url`, `mimeType`, `fileName`, and `sizeBytes`; the service checks a relative-looking storage key and image alt text, but does not inspect actual bytes. Thus the accepted MIME/type/size are metadata claims, not verification of a file.
4. Content and team DTOs accept MediaAsset IDs as references; there is no media `replace` endpoint or atomic “replace and repoint references” workflow. Updating a content object can change an image reference where that DTO permits it, but that is not the same as replacing a file while preserving every existing reference.
5. Metadata deletion checks a list of known relations before deleting the row and returns conflict when in use. The check and delete are separate. Some references such as page/theme media are schema relationships but their related modules are absent. Media deletion does **not** delete object bytes. Concurrent reference creation can race the check where database constraints do not protect the field.
6. Media list filters pagination/kind/MIME/folder; no usage-count/orphan-report endpoint or safe cleanup job was found. A storage orphan may exist because storage operations are outside this service.
7. Admin route requires session plus `media:upload` for metadata create/read and `media:delete` for metadata deletion. Root E2E tests verify permission denial, Origin rejection, DTO validation and metadata CRUD with mocked DB, not upload or storage.
8. DTO validates URL syntax as HTTP(S), declared MIME/size bounds and `storageKey` path shape. It does not verify allowed actual image format, file signature, image decode, malware, file bytes, decompression bombs, or that the supplied URL maps to the supplied key. No SSRF is established because this code does not fetch the URL; avoid adding a remote-fetch implementation without a separate threat review.
9. Replacement/removal behavior for already-referenced media has no file-level contract. Existing delete refuses known references; no cascade of references or bytes is intended/verified.

- **Previous decision:** manage existing metadata and existing URLs; no media bytes/storage contract.
- **Updated owner direction:** admins should upload, replace, reuse and remove photos/media.
- **Owner-approved implementation direction:** use a provider-neutral storage adapter and authenticated backend-proxied uploads.
- **Still pending:** select the managed storage provider and approve formats/limits, image processing and metadata handling, public/private delivery, replacement/removal semantics, orphan cleanup, budget and operational ownership. No provider has been selected or provisioned.

### H. SEO, theme and safe no-redeploy boundary
