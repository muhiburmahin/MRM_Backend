## 1. Purpose and scope

Phase 3 establishes a reviewed, reproducible PostgreSQL migration baseline and a trustworthy test foundation for the existing MRM Infotech corporate website backend. It does not implement CMS APIs or decide unapproved product policies.

This plan covers:

- An initial migration baseline strategy for the existing multi-file Prisma schema.
- All eight standalone SQL database invariants in `prisma/sql/constraints.sql`.
- Isolation and authorization gates for future disposable PostgreSQL tests.
- The repair plan for four feature-local E2E suites that presently fail compilation.
- Ownership, review gates, migration evidence, and recovery requirements.

This plan does **not** run Prisma commands, create or apply migrations, seed data, connect to PostgreSQL/Neon, provision resources, or alter files other than creating this plan document.

## 3. Migration baseline: concepts, options, and proposal

### Distinguish the four artifacts/states

1. **Prisma schema** (`prisma/schema/*.prisma`) is the declarative model used by Prisma to validate/generate a client and derive supported DDL.
2. **Migration history** (`prisma/migrations/*`) is the ordered, versioned record of DDL intended to move databases between known schema states. It is currently absent in this repository.
3. **Actual PostgreSQL state** is the database's real tables, types, constraints, indexes, migration metadata, and data. It is not discoverable from `schema.prisma` or `prisma validate`; it is currently unknown.
4. **Additional raw SQL** (`prisma/sql/constraints.sql`) expresses CHECK constraints and partial unique indexes not declared in the Prisma schema. It is not automatically applied merely because the file exists.

`prisma validate` confirms that Prisma can parse/validate the configured schema under the local Prisma version/configuration. It does **not** connect to the database, compare database objects, prove migration order, apply raw SQL, validate existing rows against checks, or demonstrate production compatibility.

### What “baseline” means here

A migration baseline is the reviewed initial migration artifact that establishes the database structure corresponding to an explicitly approved version of this schema, including approved raw-SQL invariants. The baseline becomes the first committed step in future migration history. It is not proof that an arbitrary existing DB is empty or matches the schema.

### Facts required before choosing how to initialize any environment

Before a later authorized migration task chooses an apply or adoption path, the Database Owner and Migration Reviewer must establish:

- Whether the target is a newly created empty disposable database or already contains schema objects/data.
- The exact PostgreSQL server/version and database identity, verified without exposing credentials.
- Whether Prisma migration metadata exists in that target and whether any prior schema changes were manual.
- Whether existing data violates any candidate CHECK or unique-index invariant.
- The approved schema snapshot/commit and the intended current models.
- Whether each `constraints.sql` rule is approved and whether equivalent rules already exist under other names.
- The target's production/staging separation, access role, backup/recovery path, and destruction/cleanup owner.

These facts are unavailable without an authorized environment; do not infer them from `.env.example`, local `.env` presence, Docker configuration, or the absence of local migrations.

**Recommendation:** first produce and review a schema-derived baseline and validate it only on a newly created, proven-empty disposable database. The repository evidence does not identify any existing DB, so no live-target strategy can be selected now.

### Later migration preparation and review (not authorized by this plan)

In a separate explicitly authorized implementation task:

1. Freeze/identify the approved schema revision and PostgreSQL/Prisma tool versions.
2. Generate the initial Prisma migration from the schema using a method compatible with the pinned Prisma CLI; do not hand-invent or silently edit generated model DDL.
3. Review the complete generated SQL against the schema and approved model inventory.
4. Append approved raw SQL invariants to a versioned migration in dependency order, with exact review of names, predicates, table/column existence, and duplicate-object risk.
5. Run the migration only on the explicitly verified empty disposable DB, then inspect actual catalog and `_prisma_migrations` state.
6. Run seed twice only after migration approval and verify intended repeatability/role grants using synthetic data.
7. Preserve SQL output, migration hash/history, validation output, test results, target identity proof (non-secret), reviewer approvals, and cleanup evidence.

`prisma migrate dev --create-only` is documented in `docs/database-schema.md` as still connecting to a development database. It must not be run until target identity and isolation are established. No command should rely on whatever `DATABASE_URL` happens to be in an uninspected `.env`.

### Existing database vs empty disposable database

- **Empty disposable target:** after non-secret identity verification and explicit approval, apply the reviewed initial migration normally. Confirm there are no pre-existing user tables or migration records before applying.
- **Existing/shared/staging/production target:** do not run the initial create migration. A separately approved read-only inventory must compare catalog objects, data, constraints, indexes, and migration metadata with the proposed baseline. Then use a reviewed adoption path only if exact equivalence is proven; otherwise make a forward-only reconciliation plan.
- Never mark a migration as applied merely to silence a pending migration. Never point an initial migration at production to “see what happens.”

### Failure, rollback, and recovery

- Before any persistent target migration: capture a restorable backup/snapshot and prove the restore path in a non-production environment; record an owner and recovery point.
- For disposable test targets, the approved recovery may be to destroy/recreate the disposable DB/branch, but only by the named owner and after verifying target identity.
- For shared persistent environments, do not promise transactional rollback for arbitrary DDL. Prepare forward-fix or restore procedures and an explicit outage/data-loss decision before apply.
- On any unexpected object, data conflict, lock timeout, partial migration, failed constraint, or target identity mismatch: stop immediately, preserve logs without secrets, do not retry or manually repair, and escalate to the Database Owner and Migration Reviewer.

### Raw SQL lifecycle and verification

- Keep database-only rules in versioned migration SQL, reviewed alongside the Prisma-generated DDL. The standalone source file is not applied automatically. The Migration Reviewer must decide how it remains a reference without creating two competing sources of truth.
- Do not change or execute `constraints.sql` during planning. At implementation time, check table/column names against generated migration DDL, verify object names are collision-free, and use exact SQL review.
- Before creating constraints on any existing data, run read-only conflict queries on an authorized disposable copy. Do not “fix” violating rows automatically: decide with the data/product owner whether to remediate, preserve, or defer the rule.
- After migration, inspect PostgreSQL catalogs for all six CHECK constraints and both partial indexes, including index predicates. Then test both permitted and prohibited writes in a disposable DB and run corresponding application-level tests.
- DB tests establish enforcement for all write paths. Application tests establish useful validation/errors and publication behavior. Neither category substitutes for the other.

## 5. Test database safety and isolation protocol

### Existing verified safeguards

- The configured root E2E setup uses a synthetic local test URL and the Nest helper overrides `PrismaService` with `FakePrisma`.
- This makes current root E2E tests mocked; it does not validate a PostgreSQL environment.
- The repository has Prisma scripts that can contact a database (`prisma:seed`, `migrate:dev`, `migrate:deploy`, `migrate:status`). There is no verified guard proving their `DATABASE_URL` target is disposable.
- No real integration DB identity, CI credential setup, Neon branch lifecycle, or responsible owner was verified.

### Proposed protocol (requires approval before implementation)

1. **Provisioning and identity**
   - Database Owner creates a dedicated disposable PostgreSQL database/Neon branch through an authorized process; no production/shared branch reuse.
   - Before any migration, seed, reset, or integration test, verify target identity using non-secret provider project/branch identifiers and server/database metadata. Never echo a URL or credentials.
   - Enforce an explicit test-target allowlist and deny production/staging identities in the future DB-test harness. If identity cannot be proved, fail closed.
2. **Credentials and least privilege**
   - CI obtains short-lived or scoped test-only credentials from its secret manager; no credentials in source, logs, artifacts, command output, or checked-in `.env`.
   - Test role has access only to the disposable target and cannot access production. Migration/cleanup privileges are separate and owned by approved operators.
3. **Environment separation**
   - Keep development, staging, production, and test project/branch/database identities and secrets separate.
   - Avoid implicit `DATABASE_URL` fallback to a developer's general `.env` for DB integration tasks. Require explicit test-target configuration.
   - Prohibit destructive commands unless the target identity guard has succeeded and the operator has an approved runbook.
4. **Fixture isolation and cleanup**
   - Use synthetic fixtures with unique test-run identifiers; wrap tests in transactions or use per-worker schemas/branches only after their isolation behavior is proven.
   - Clean only records/schema created by that test run; never issue broad reset/drop/truncate commands against an unverified target.
   - Cleanup runs under the test owner, is logged without secrets, and is verified. Expire/destroy disposable branches according to an assigned owner and retention rule.
5. **CI and test classification**
   - Label current FakePrisma HTTP E2E as `mock-based`; label future database tests explicitly as PostgreSQL integration tests.
   - CI should run mock suites without a DB secret. PostgreSQL integration tests run in a separate job with a disposable DB provisioned for that job.
   - A failure to obtain/prove a disposable test target must fail or mark the integration job blocked; never fall back to another environment.
6. **Ownership and incidents**
   - Database Owner: provisioning, target identity, access, backup/snapshot, and branch lifecycle.
   - Test/CI Owner: scripts, fail-closed guard, synthetic fixtures, execution evidence, cleanup automation.
   - Migration Reviewer: SQL/schema review and migration-history integrity.
   - Release Approver: any later promotion beyond disposable testing.
   - These named roles are currently **UNASSIGNED — OWNER REQUIRED**. Define incident contact/escalation before DB tests.

No item in this proposed protocol should be described as currently implemented unless separately verified.
